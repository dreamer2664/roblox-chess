# Piece meshes

The pieces are real geometry, not stacked primitives. They are generated by
[`tools/make_pieces.py`](../tools/make_pieces.py) and live in
[`assets/pieces/`](../assets/pieces) as Wavefront OBJ files.

## Why generated

Round one shipped pieces assembled from Roblox primitives. They read as boxes and
were rejected. The obvious fix — downloading a CC0 set (Polyhaven's `chess_set`) —
doesn't survive contact with Roblox: that set is roughly 55k triangles *per piece*
with PBR texture maps, so a full board would be ~1.7M triangles and 32 texture
sets. Roblox's per-place triangle budget and the mobile renderer both say no.

So the meshes are built from turned profiles instead:

| piece | triangles | height (studs) | base diameter | construction |
| --- | --- | --- | --- | --- |
| pawn | 3,304 | 3.16 | 2.40 | lathe |
| rook | 2,536 | 4.35 | 2.54 | lathe + 6 merlons |
| knight | 3,164 | 4.77 | 2.60 | 30×20 elliptical sweep + lathe base |
| bishop | 4,240 | 4.91 | 2.68 | lathe + finial |
| queen | 4,140 | 5.75 | 2.82 | lathe + 9 point-teeth + finial |
| king | 3,496 | 6.67 | 2.96 | lathe + cross |

**41,760 triangles for a full 32-piece set.** That is about 1/40th of the
Polyhaven path, and it is one draw-friendly mesh per piece.

Proportions follow a real tournament Staunton set (king 95 mm, pawn 45 mm, base
38–42 mm) measured against a 57 mm square, then scaled so one board square is 4
studs (`Config.TileSize`). Every base is 60–74% of its square, which is what
makes a board read as a real chess set rather than abstract blobs.

## Regenerating

```bash
python3 tools/make_pieces.py            # rewrite assets/pieces/*.obj + manifest.json
python3 tools/make_pieces.py --check    # CI: fail if the committed meshes are stale
python3 tools/piece_sheet.py            # renders/06_piece_sheet.png QA sheet
```

The generator is deterministic: no randomness, no external inputs. `--check`
regenerates in memory and compares byte-for-byte with what is committed.

## Getting them into Studio

`Config.Meshes` ships with `meshId = 0`, which keeps every piece on the
primitive fallback build. The game is playable immediately after `rojo serve`;
the meshes are an upgrade, not a dependency.

1. In Studio: **Asset Manager → Import 3D**, pick all six files in
   `assets/pieces/`. Import with *scale = 1* and *Y-up*; the OBJs are already in
   studs with the origin at the base of the piece.
2. Copy each resulting asset id into `Config.Meshes`:

   ```lua
   Config.Meshes = {
       P = { meshId = 1234567890, size = Vector3.new(1.24, 3.16, 1.24), yaw = 0 },
       ...
   }
   ```

   `size` and `yaw` are already correct — they are generated from
   `manifest.json` by the same script that builds the meshes.
3. Nothing else changes. `PieceLibrary.build` switches to `MeshPart` as soon as
   any `meshId` is non-zero, keeping the piece anchored, non-queryable and
   positioned at the base of its square.

The knight mesh faces +Z. `PieceLibrary` turns it 180° for White and 0° for Black (the
configured `yaw` plus a half turn for Black), so both sides face their opponent, like a
real set.

## Custom pieces

Any OBJ with +Y up and its origin at the base works — the loader only needs
`size` (bounding box in studs) and `yaw`. Keep the triangle count under ~5k per
piece and stay away from baked textures: colour comes from `Part.Color`, so
`Config.Colors.WhitePiece` / `BlackPiece` restyle the whole set.
